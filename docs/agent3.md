# Project-Wide Domain And Persistence Refactoring Rules

## Purpose

Use these rules when refactoring any module in the project. The target architecture is a rich domain model with explicit application orchestration, persistence-oriented repositories, and infrastructure adapters that contain storage mechanics rather than business decisions.

Apply the rules incrementally. Preserve external contracts and existing behavior unless a task explicitly changes them.

## Simplicity First

- Prefer the simplest implementation that makes the behavior obvious.
- Optimize for readability before abstraction, reuse, or theoretical extensibility.
- Consistency is valuable, but not when it creates repetitive types, wrappers, builders, factories, or indirection that do not clarify behavior.
- Add an abstraction only when it protects a real boundary, expresses a business concept, or removes meaningful duplication.
- Keep straightforward code straightforward. Do not introduce patterns merely to make every module look structurally identical.
- Prefer a short explicit workflow over generic machinery that requires readers to navigate several files.

## Domain Modeling

- Give each domain concept one authoritative class. Do not create parallel classes for the same concept merely because creation, editing, or persistence uses different subsets of data.
- Create an entity when a concept has identity, lifecycle, state transitions, or cross-field invariants.
- Use value objects for validated scalar concepts and small cohesive values.
- Do not introduce an entity or process object that only renames a value, forwards calls, or duplicates application orchestration.
- Keep projection fields, transport fields, and persistence-only details outside a domain entity unless its behavior requires them.

## Identity And Construction

- An ID generated by persistence may be absent only before the entity is inserted.
- Use a named `create(...)` factory for new entities. Accept only the values available at creation and establish a valid initial state.
- Use a named `restore(...)` factory for persisted entities. Require the identity and complete domain state needed by future behavior.
- Return the restored entity from repository creation when the database generates its identity.
- Prefer natural or composite domain identity when a surrogate database ID has no domain meaning.
- Do not add fake IDs, timestamps, or default values merely to make creation and restoration share one input shape.

## Domain Behavior

- Put business rules, invariants, lifecycle transitions, and state-dependent decisions in domain methods.
- Name behavior by intent, such as `accept()`, `cancel()`, `complete()`, `reschedule()`, or `changeDetails()`.
- A domain method may receive related entities or value objects explicitly when a rule depends on them.
- Domain methods may mutate aggregate state or return the entities/value objects changed by the operation.
- Return `void` when a domain method only changes entity state.
- Return useful changed data when the application needs it.
- Throw a domain error when a business rule prevents the operation.
- Do not return `{ kind: ... }`, booleans, or named outcome types for ordinary domain transitions.
- Domain code must not execute SQL, depend on NestJS, know HTTP contracts, access request context, or call infrastructure providers.
- The domain layer must never import from the application, infrastructure, or presentation layers. Dependencies point inward: outer layers may import domain code, never the reverse.
- Do not duplicate a domain invariant in a use case or SQL branch merely to make it visible.
- Keep database constraints as defense in depth even when the domain enforces the same invariant.

## Domain Errors And HTTP Mapping

- All domain errors extend the transport-neutral `DomainError` hierarchy in `common/domain/errors`.
- Use `DomainValidationError`, `DomainNotFoundError`, and `DomainConflictError` as the common semantic categories.
- Throw explicit module/domain errors such as `InvalidCrewNameError` or `ParticipationRequestNotPendingError`; entities and value objects must not instantiate a generic category with free-form message text.
- Give each explicit domain error a fixed message in its constructor. Call sites instantiate it without supplying text.
- Keep customization reasonable: create one error per meaningful violation concept, not one class for every conditional branch when several checks represent the same invalid concept.
- Every explicit error converges on a common semantic category such as validation, not found, or conflict so presentation mapping remains centralized.
- Do not create an application copy solely for HTTP mapping.
- Domain errors contain no HTTP status, NestJS type, application dependency, or persistence detail.
- The global presentation exception filter maps domain validation to HTTP 400, domain not-found to HTTP 404, and domain conflict to HTTP 409.
- Application errors remain appropriate for failures discovered by orchestration, such as an absent repository lookup, authentication, authorization, or unavailable dependency.
- Translate a domain error in the use case only when its external meaning differs or exposing it would reveal protected state.
- Unknown and infrastructure errors map to HTTP 500.

## Application Use Cases

- A command use case should visibly orchestrate the workflow: load domain state, invoke domain behavior, persist changed state, and trigger required external effects.
- Keep transaction ownership, authorization context, external storage, messaging, notifications, and cache invalidation in the application layer.
- Convert `undefined` lookups and domain errors into the appropriate application/API meaning when translation is required; otherwise allow categorized domain errors to reach the global exception filter.
- Do not hide business decisions inside repositories or SQL adapters.
- Do not reimplement domain transitions with conditionals in the use case.

Example:

```ts
await unitOfWork.run(async () => {
  const aggregate = await repository.findByIdForUpdate(id);
  if (!aggregate) throw new AggregateNotFoundError();

  const relatedEntities = await repository.findRelatedForUpdate(id);
  const changedEntities = aggregate.performAction(actorId, relatedEntities);

  await repository.save(aggregate);
  await repository.saveAll(changedEntities);
});
```

## Repository Abstractions

- Repositories expose persistence vocabulary: `create`, `findById`, `findByIdForUpdate`, `save`, `saveAll`, and `delete`.
- Return domain entities from command repositories, not SQL rows, transport DTOs, or presentation projections.
- `findByIdForUpdate` returns the complete domain state required to rehydrate the entity and locks the rows required for the pending mutation.
- Load related collections explicitly when they are not intrinsic to every operation. Do not make every aggregate lookup load an entire object graph.
- Repositories map between domain and persistence representations. They do not decide state transitions, select defaults that belong to the domain, choose successors, or implement business policy.
- Repositories return the simplest persistence result and never decide which application error to throw. The application interprets `undefined`, `false`, or another simple result in the context of its use case.
- A repository implementation must not import a concrete application error merely to translate an expected persistence result.
- For command loading, `findByIdForUpdate` maps the database row through the entity's `restore(...)` factory and returns `undefined` when no row is available.
- `save` persists state already decided by the domain. It must not invent a transition.
- Persist related changes in a set-based bulk operation rather than issuing one query per entity.
- Execute related reads and writes inside an application-owned unit-of-work transaction.

## Return-Type Convention

Choose a return type based on meaning, not on the SQL statement used internally.

In short: use domain exceptions for rejected business behavior, `undefined` for missing lookups, the simplest persistence result for mutations, and `kind` only for genuinely complex branching.

### Queries

- Return `Entity | undefined` when absence is the only expected alternative to finding one entity.
- Return an array for a collection; use an empty array when no items exist.
- Return `null` only when a record exists but a particular stored value is nullable.
- Use `boolean` only for genuine yes/no questions such as `exists`, `isOwnedBy`, `matches`, or `hasPermission`.

### Commands And Mutations

- Return the created entity from `create` when persistence generates identity or other required domain state.
- `create()` returns the created entity. It may return `undefined` when one normal missing-parent/target case must be represented.
- Return `void` from `save`, `saveAll`, and other mutations when no expected result needs interpretation.
- Return `boolean` when the application must distinguish affected from not affected and those are the only two expected results. The application—not the repository—chooses the corresponding error.
- `delete()` returns `void` after the entity was loaded, or `boolean` for a direct delete where absence is meaningful.
- Unexpected database and concurrency failures throw infrastructure errors.
- Use a discriminated union with `kind` when two or more expected outcomes require different caller behavior.
- Do not return `boolean` when `false` has more than one meaning. Use it only for one clear binary persistence result such as affected/not affected.
- Do not return `{ kind: 'saved' }` or `{ kind: 'updated' }` when no alternative outcome exists; use `void` or return the persisted entity.
- Do not use `kind` for simple `saved/not-found`, `changed/not-pending`, or `created/not-found` cases.
- Use `kind` only for several legitimate, meaningfully different paths containing different data.

Example:

```ts
type SaveOutcome = { kind: 'saved' } | { kind: 'not-found' } | { kind: 'version-conflict'; currentVersion: number };
```

Use outcome names that describe domain/application meaning. Avoid leaking database terminology such as `zero-rows`, `constraint-23505`, or `update-failed`.

### Layer Ownership

- Define public outcome types in the application layer next to the port or application models.
- SQL adapters may return affected rows or low-level internal results, but the repository must normalize them into the port's return type.
- A use case should handle every expected outcome exhaustively and translate it to the appropriate application result or error.
- Unexpected database, network, and programming failures remain exceptions and must not be converted into expected `kind` outcomes.
- Define explicit outcome types only at stable boundaries that need a declared contract, such as application ports. Do not create named outcome types for local or entity-internal inference.
- Do not reuse an infrastructure result as a public contract merely because its shape is convenient.

## SQL Adapter Naming And Placement

- Name a SQL adapter after the repository operation it implements.
- Place reads under `persistence/reads/` and writes under `persistence/writes/`.
- Prefer names such as `FindByIdForUpdateSql`, `FindRelatedForUpdateSql`, `CreateSql`, `SaveSql`, `SaveAllSql`, and `DeleteSql`.
- Do not name a general persistence adapter after a use case or business process.
- Keep one cohesive persistence operation per SQL adapter. Split unrelated reads and writes.
- Keep RLS enforcement, row locking, constraints, timestamps, joins, aggregation, pagination, concurrency guards, and set-based writes in SQL.
- Do not encode domain lifecycle decisions in SQL. SQL persists the transition selected by the domain.

## Read Models And CQRS

- Query repositories may return application read models optimized for their consumers.
- Do not rehydrate aggregates for feeds, lists, counts, summaries, pagination, or other read-only projections.
- Query SQL may join, aggregate, rank, filter, and paginate. These are retrieval responsibilities, not domain transitions.
- Keep command repositories and query repositories separate when their shapes and responsibilities differ materially.

## Compatibility And Verification

- Preserve routes, request/response schemas, status codes, events, and other externally observable behavior unless explicitly instructed otherwise.
- Add focused tests for domain invariants and lifecycle transitions.
- Add integration coverage for repository mapping, transactions, RLS behavior, locking, and bulk persistence when affected.
- Run TypeScript checks, architecture lint, relevant tests, migration validation when schema or policy changes, and `git diff --check`.
- Treat a naming-only refactor as behavior-preserving and verify dependency-injection wiring after moving providers.
